# 操作系统：经典同步互斥问题——读者-写者问题

> **导语**
> 本节课我们将学习操作系统中另一个极其经典的进程同步互斥模型：**读者-写者问题**。
> 与生产者-消费者问题侧重于“同步”不同，读者-写者问题侧重于解决**极其复杂的互斥关系**。我们将一步步推演如何实现“允许多个读者同时读”，以及如何解决因为“读优先”而导致的“写者饿死”问题。

---

## 一、 问题描述与要求分析

### 1. 场景描述

系统中存在一个**共享文件**（或数据结构），有两种类型的进程对其进行访问：

- **读者进程 (Reader)**：只负责读取文件内容，不修改数据。
- **写者进程 (Writer)**：向文件中写入新内容，会修改数据。

### 2. 访问控制要求 (核心规则)

1.  **允许多个读者同时对文件执行读操作**。（因为读操作不会改变数据，不会产生冲突）。
2.  **只允许一个写者往文件中写信息**。（两个写者同时写会导致数据覆盖，必须互斥）。
3.  **任一写者在完成写操作之前不允许其他读者或写者工作**。（写者与读者、写者与写者之间绝对互斥）。
4.  **写者执行写操作前，应让已有的读者和写者全部退出**。

---

## 二、 基础版实现：读者优先算法

要实现复杂的互斥逻辑，核心在于引入一个**整型计数器 `count`**。

### 1. 信号量与变量设置

- `int count = 0;`：记录当前有几个读进程正在访问文件。
- `semaphore rw = 1;`：(Read/Write) 用于保证读者和写者、写者和写者对**共享文件**的互斥访问。
- `semaphore mutex = 1;`：用于保证对**共享变量 `count`** 的互斥访问（防止“检查+修改”无法一气呵成）。

### 2. 基础版代码实现

```c
semaphore rw = 1;     // 用于实现对共享文件的互斥访问
int count = 0;        // 记录当前有几个读者在访问文件
semaphore mutex = 1;  // 用于实现对 count 变量的互斥访问

// 读者进程
reader() {
    while(1) {
        P(mutex);           // 1. 各个读进程互斥访问 count 变量
        if (count == 0) {   // 2. 如果自己是第一个读者...
            P(rw);          // 3. ...则负责对共享文件加锁，阻止写者进入
        }
        count++;            // 4. 读者数量 +1
        V(mutex);           // 5. 释放对 count 的锁

        读文件...           // --- 真正执行读操作的临界区 ---

        P(mutex);           // 6. 各个读进程互斥访问 count 变量
        count--;            // 7. 读者数量 -1
        if (count == 0) {   // 8. 如果自己是最后一个退出的读者...
            V(rw);          // 9. ...则负责对共享文件解锁，允许写者进入
        }
        V(mutex);           // 10. 释放对 count 的锁
    }
}

// 写者进程
writer() {
    while(1) {
        P(rw);              // 1. 写者申请对共享文件加锁

        写文件...           // --- 真正执行写操作的临界区 ---

        V(rw);              // 2. 写者释放对共享文件的锁
    }
}
```

### 3. 基础版致命缺陷：写者饿死 (读优先)

- **现象推演**：如果读者源源不断地到来。
  - 第一个读者进入，`count=1`，执行 `P(rw)` 锁住了文件。
  - 此时一个写者到来，执行 `P(rw)` 被**阻塞等待**。
  - 紧接着，第二个、第三个读者到来。因为此时 `count > 0`，它们**跳过了 `P(rw)` 的检查，直接进入文件开始读**！
  - 只要有任何一个读者还在文件里，`count` 就不为 0，最后那个 `V(rw)` 就永远不会执行。
- **结果**：只要有源源不断的读者，写者就会一直被阻塞在 `P(rw)` 处，导致**写者饿死**。这被称为“读优先”。

## 三、 进阶版实现：读写公平法 (解决写者饿死)

为了防止读进程插队导致写进程饿死，我们再增加一个互斥信号量 `w`。

### 1. 新增信号量

- `semaphore w = 1;`：用于实现**“先来先服务”**的相对公平机制，防止新来的读者在写者排队时强行插队。

### 2. 进阶版代码实现 (核心在于 `P(w)` 和 `V(w)` 的位置)

```c
semaphore rw = 1;     // 用于实现对共享文件的互斥访问
int count = 0;        // 记录当前有几个读者在访问文件
semaphore mutex = 1;  // 用于实现对 count 变量的互斥访问
semaphore w = 1;      // 用于实现“写优先/读写公平”的排队机制

// 读者进程
reader() {
    while(1) {
        P(w);               // ⚡️⚡️ 1. 申请过排队闸机 (有写者在等时，新读者将被拦在这)
        P(mutex);           // 2. 互斥访问 count
        if (count == 0) {
            P(rw);          // 3. 第一个读者锁文件
        }
        count++;
        V(mutex);           // 4. 释放 count 锁
        V(w);               // ⚡️⚡️ 5. 释放闸机 (自己已登记进场，让后面的人排队)

        读文件...

        P(mutex);
        count--;
        if (count == 0) {
            V(rw);          // 最后一个读者解锁文件
        }
        V(mutex);
    }
}

// 写者进程
writer() {
    while(1) {
        P(w);               // ⚡️⚡️ 1. 写者抢占闸机，阻止后续读/写者进入
        P(rw);              // 2. 申请对文件加锁 (如果里面有读者，写者阻塞在这)

        写文件...

        V(rw);              // 3. 释放文件锁
        V(w);               // ⚡️⚡️ 4. 释放排队闸机
    }
}
```

### 3. 公平机制逻辑推演 (为什么不会饿死写者了？)

假设场景：`读者A` 正在读文件 $\rightarrow$ `写者B` 到达 $\rightarrow$ `读者C` 到达。

1.  **读者A 在读**：`w` 是释放的，但 `rw` 已被读者A锁住（因为它是第一个读者）。
2.  **写者B 到达**：
    - 执行 `P(w)` 成功，进入闸机（此时 `w=0`）。
    - 执行 `P(rw)`，因为文件被读者A锁着，**写者B 阻塞等待**。
3.  **读者C 随后到达**：
    - 执行 `P(w)`。由于写者B 刚才霸占了 `w`，**读者C 被死死拦在了闸机外**，无法去执行后面的 `count++` 插队代码！
4.  **死锁破局**：
    - 读者A 读完离开，执行 `V(rw)` 解锁文件。
    - 写者B 被唤醒，进入临界区写文件！
    - 写者B 写完离开，依次执行 `V(rw)` 和 `V(w)`。
    - 闸机放开，读者C 这才得以进入。

**结论**：新增的 `w` 信号量就像一个排队闸机。写者一旦排队，后面的读者就必须乖乖在闸机外等着，绝杀了读进程“无限插队”的可能。

## 四、 本节核心经验总结 (大题必备)

1.  **核心思想提取**：
    遇到**“某一类进程允许多个同时访问，而另一类进程必须绝对互斥访问”**的复杂互斥问题，立刻联想到**读者-写者模型**。
2.  **计数器妙用**：
    利用一个计数器 `count`：
    - **第一个来的**负责加“大锁”（锁整个资源）。
    - **中间来的**只负责把 `count++`。
    - **最后一个走的**负责解“大锁”。
3.  **互斥保护计数器**：
    对计数器 `count` 的检查和修改操作必须**一气呵成**，务必用一个互斥信号量 `mutex` 把 `count` 的操作代码给夹起来。
