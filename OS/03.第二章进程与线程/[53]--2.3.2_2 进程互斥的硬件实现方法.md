# 操作系统：进程互斥的硬件实现方法

> **导语**
> 上一节我们学习了进程互斥的四种软件实现方法，发现软件方法（如双标志先检查法）失败的根本原因在于“检查”和“上锁”不能一气呵成。本节课我们将学习三种由**底层硬件机制**保障的互斥实现方法：中断屏蔽方法、Test-and-Set 指令（TSL）和 Swap 指令。通过硬件的支持，我们可以完美解决操作被打断的问题。

---

## 一、 中断屏蔽方法

这是一种利用底层硬件开关中断的最简单粗暴的方法。我们在之前学习“原语”时就接触过这种机制。

### 1. 实现原理

在一个进程开始访问临界区之前，执行**关中断 (Disable Interrupts)** 指令；在访问完临界区后，执行**开中断 (Enable Interrupts)** 指令。

```c
// 进程 P0
关中断;         // 关中断后，当前 CPU 不再响应任何外部中断，也不会发生进程切换
临界区;         // 此时只有 P0 能独占执行这段代码，绝对安全
开中断;         // 解除中断屏蔽，允许其他进程被调度
剩余区;
```

### 2. 优缺点分析

- **优点**：实现极其简单、逻辑清晰，效率非常高。
- **缺点 (重点考点)**：
  1.  **不适用于多处理机系统**。关中断指令只能对执行该指令的**当前这一个 CPU** 起作用。在多核系统中，处理机 A 关了中断，处理机 B 仍在正常调度，此时若处理机 B 上的进程也想访问该临界区，依然会发生同时进入的冲突。
  2.  **不适用于用户级进程**。开/关中断指令属于**特权指令**，只能在内核态下由**操作系统内核进程**执行。如果允许普通用户级进程随便关中断，它可能永远不执行开中断，直接导致整个系统瘫痪。

## 二、 Test-and-Set 指令 (TS/TSL 指令)

TSL (Test-and-Set Lock) 指令由**硬件直接实现**。在执行该指令的过程中，**不允许被任何中断打断**，保证了操作的原子性（一气呵成）。

### 1. 硬件逻辑原理

系统为临界区设置一个布尔型共享变量 `lock`。

- `lock = false` 表示临界区未上锁（空闲）。
- `lock = true` 表示临界区已上锁（忙碌）。

以下是用 C 语言描述的 **TSL 硬件指令在背后偷偷完成的原子操作逻辑**：

```c
// 下面这整个函数是由硬件电路一气呵成执行完的，绝对不会被打断！
bool TestAndSet(bool *lock) {
    bool old = *lock;  // 1. 记录以前是否上锁
    *lock = true;      // 2. 不管三七二十一，先把锁设为 true (上锁)
    return old;        // 3. 返回以前的锁状态
}
```

### 2. 互斥使用方法

利用这个硬件指令，进程进入临界区的代码可以这样写：

```c
// 某个进程 Pi
while (TestAndSet(&lock));  // ① 进入区：如果旧值是 true，说明别人锁了，死循环等待；
                            //            如果旧值是 false，说明以前空闲，此时已被硬件设为 true (上锁成功)，跳出循环！
临界区代码;                 // ② 临界区
lock = false;               // ③ 退出区：自己用完后，把锁解开
剩余区代码;                 // ④ 剩余区
```

### 3. 优缺点分析

- **优点**：实现简单，由于有硬件支持，完美解决了软件实现中“检查和上锁不能一气呵成”的问题；并且**适用于多处理机环境**。
- **缺点**：**违背了“让权等待”原则**。如果暂时进不去临界区，进程会被卡在 `while` 循环里，不断在 CPU 上空转测试，发生“忙等待”，浪费 CPU 资源。

## 三、 Swap 指令 (XCHG / Exchange 指令)

Swap 指令与 TSL 指令类似，也是由**硬件实现的一气呵成**的原子指令。

### 1. 硬件逻辑原理

顾名思义，Swap 的作用就是**交换两个变量的值**。

```c
// 硬件一气呵成执行的交换逻辑
void Swap(bool *a, bool *b) {
    bool temp;
    temp = *a;
    *a = *b;
    *b = temp;
}
```

### 2. 互斥使用方法

为临界区设置共享变量 `lock`（初值为 `false`）。每个进程准备一个私有变量 `old`（初值为 `true`）。

```c
// 某个进程 Pi
bool old = true;
while (old == true) {
    Swap(&lock, &old);      // ① 进入区：不断把 lock 的值换到私有变量 old 里。
                            // 若 lock 是 true，换完 old 还是 true，继续循环；
                            // 若 lock 是 false，换完 old 变成 false (且 lock 变 true 锁上)，跳出循环！
}
临界区代码;                 // ② 临界区
lock = false;               // ③ 退出区：自己用完后，解锁
剩余区代码;                 // ④ 剩余区
```

### 3. 与 TSL 指令的对比

在逻辑层面上，**Swap 指令与 TSL 指令做的事情几乎是一模一样的**：

- 都是把 `lock` 设置为 `true`。
- 都是取出 `lock` **修改之前**的旧值。
- 都是根据旧值判断是否需要继续死循环。

因此，**Swap 指令的优缺点与 TSL 指令完全一致**：实现简单、支持多处理机环境，但**同样违背了“让权等待”原则**，会导致忙等待。

## 四、 本节知识脉络速记

| 硬件实现方法      | 适用环境     | 指令权限       | 核心原理                               | 是否满足“让权等待”？                          |
| :---------------- | :----------- | :------------- | :------------------------------------- | :-------------------------------------------- |
| **中断屏蔽法**    | 仅单核处理机 | 仅内核特权指令 | `关中断 -> 临界区 -> 开中断`           | 不满足 (更严重，连切换都不允许)               |
| **TS / TSL 指令** | 支持多处理机 | 普通指令       | 硬件保证“读旧值+设为true”一气呵成      | **不满足** (一直在 CPU 上 `while` 死循环空转) |
| **Swap / XCHG**   | 支持多处理机 | 普通指令       | 硬件保证“私有变量与锁状态交换”一气呵成 | **不满足** (一直在 CPU 上 `while` 死循环空转) |

> **思考提示**：本节介绍的硬件指令虽然完美解决了互斥安全问题，但都逃不开一个致命弱点——**违背了“让权等待”原则，导致忙等待**。那么，有没有一种机制，既能安全实现互斥，又能在进不去临界区时让进程乖乖“去睡觉（阻塞挂起）”交出 CPU 呢？这就是我们下一节要隆重介绍的终极武器：**信号量机制**。
